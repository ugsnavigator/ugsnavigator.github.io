# Перспективний план: персональний кабінет

## Мета

Додати персональний кабінет для завуча або директора. Користувач реєструється, входить у свій обліковий запис і з будь-якого пристрою бачить власні налаштування закладу та збережені накази.

На першому етапі не передбачаються спільний кабінет школи, запрошення інших працівників, ролі або розмежування доступу між кількома користувачами одного закладу. Кожен обліковий запис є незалежним і володіє лише власними даними.

## Запланований стек

- **Firebase Authentication** — реєстрація та вхід через email/пароль і, за потреби, Google; підтвердження email, відновлення пароля та керування сесією.
- **Cloud Firestore** — налаштування закладу, довідник працівників і структуровані дані збережених наказів.
- Поточний статичний інтерфейс і клієнтська генерація DOCX залишаються без окремого прикладного сервера.
- `IndexedDB`/`localStorage` використовуються як тимчасовий локальний кеш і джерело даних для одноразової міграції після першого входу.

Firebase обрано замість реляційної бази, оскільки запланована модель не має спільних шкіл, ролей чи складних зв'язків: усі дані природно ізолюються за `uid` власника.

## Модель даних

Орієнтовна структура Firestore:

```text
users/{uid}
  profile                         основні відомості облікового запису
  settings/school                 реквізити та налаштування закладу
  directories/employees          довідник працівників
  orders/{orderId}                збережені накази
```

Кожен наказ зберігається як структурований запис: шаблон, номер, дата, статус, реєстраційна серія, значення полів, дати створення та оновлення. Готовий DOCX на першому етапі не завантажується в хмару — він повторно формується у браузері з актуальних даних.

Великі зображення, зокрема графічний бланк, не слід безконтрольно вбудовувати в документи Firestore. Перед реалізацією потрібно або встановити обмеження й стискання зображення, або зберігати його окремо у Cloud Storage.

## Модель доступу

Базове правило: авторизований користувач може читати й змінювати лише гілку `users/{uid}`, де `uid` збігається з ідентифікатором його сесії.

```javascript
rules_version = '2';

service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{userId} {
      allow read, write:
        if request.auth != null
        && request.auth.uid == userId;

      match /{document=**} {
        allow read, write:
          if request.auth != null
          && request.auth.uid == userId;
      }
    }
  }
}
```

Перед запуском ці правила потрібно доповнити перевірками дозволених полів, типів даних і максимальних розмірів. Firebase client config та API key можуть бути у клієнтському коді; адміністративні ключі й облікові дані сервісного акаунта — ніколи.

## Етапи впровадження

1. Створити окремий Firebase-проєкт для production і налаштувати дозволені домени.
2. Додати екрани реєстрації, входу, підтвердження email, відновлення пароля та виходу.
3. Реалізувати сховище Firestore за окремим інтерфейсом, не змішуючи його безпосередньо з UI та генератором DOCX.
4. Перенести профіль закладу, довідник працівників і накази з локального сховища у хмару.
5. Після першого входу запропонувати одноразовий імпорт наявних локальних даних. Повторний запуск міграції не повинен створювати дублікати або перезаписувати новіші записи.
6. Залишити локальний кеш незбереженої форми та передбачити зрозумілі стани: синхронізовано, зберігається, немає мережі, помилка синхронізації.
7. Додати експорт усіх даних облікового запису та повне видалення облікового запису разом із його даними.
8. Оновити CSP: поточне `connect-src 'none'` несумісне з Firebase. Дозволити лише конкретні Firebase endpoints, потрібні застосунку.
9. Перевірити Firestore Rules через Emulator Suite та автоматичні тести на доступ до чужого `uid`.
10. Оновити політику конфіденційності, повідомлення про обробку персональних даних і документацію щодо резервного копіювання.

## Критерії готовності

- неавторизований відвідувач не може прочитати або змінити хмарні дані;
- користувач не може отримати доступ до даних іншого `uid`, навіть підмінивши запит у консолі браузера;
- налаштування закладу й накази відновлюються після входу на іншому пристрої;
- локальна міграція є одноразовою, відновлюваною після помилки й не створює дублікатів;
- втрата мережі не призводить до тихої втрати введених даних;
- видалення облікового запису видаляє пов'язані хмарні дані;
- генерація та нормативна перевірка DOCX не залежать від доступності Firebase після завантаження необхідних даних.

## Не входить у перший етап

- спільний кабінет закладу;
- ролі директора, завуча, адміністратора або переглядача;
- запрошення працівників і спільне редагування наказів;
- централізоване погодження чи підписання документів;
- зберігання готових DOCX як офіційного електронного архіву.
